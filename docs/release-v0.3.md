# OpenSourceRail v0.3.0

v0.3 makes the project boundary more credible while strengthening the most
adoptable product: deterministic city design, delivery planning and owner/
operator evidence management.

## Release highlights

- City Studio, civil IFC generation and CI use one portable Python-runtime
  resolver; browser acceptance provisions the pinned IFC stack it exercises.
- The root front door presents three products with distinct maturity and keeps
  the first adoption path non-safety.
- Headline economics use appropriately rounded domestic-value figures; the
  exact foreign-turnkey comparison remains a reproducible sensitivity model.
- LM3 battery terminology now defines externally accessed, saloon-isolated
  side enclosures beneath the seat zone with outward-only drainage and venting.
- The cost and station sources agree that a `halt` has no charger or energy
  site; powered station archetypes retain their charging allowance.
- EN 50716:2023, IEC 62278-1:2025, IEC 62267:2009 and IEC 62290-1:2025 are
  organised in one maintained standards baseline.
- Commodity Raspberry Pi/Radxa equipment remains the pilot/application path,
  while revenue-service safety channels now have a separate assessor-controlled
  industrial safety-MCU selection gate.
- Fast ATP expired-authority and interlocking validity-window arithmetic proofs
  run in CI. Topology-heavy ATP and interlocking proofs remain bounded formal
  evidence, not ordinary-CI claims, until their unwind limits are frozen and
  reviewed.
- A documented SMRaft-to-Rust abstraction map improves reviewability without
  misrepresenting it as a machine-checked refinement proof.

## Deliberately not claimed

v0.3 is not a safety certificate, construction release, production drawing set,
supplier freeze or revenue-service GoA 4 system. Physical train/civil proof,
qualified safety hardware, combined deployment charging cases, structural and
geotechnical validation, independent assessment and regulator acceptance remain
explicit gates in the certification and discipline checklists.

## Assessment disposition

| Recommendation | v0.3 decision |
|---|---|
| Restore integration health and share one Python runtime | Implemented and covered by Rust, Python and browser acceptance. |
| Separate commodity application hosts from safety channels | Implemented as an architecture and controller-selection gate; hardware is not frozen. |
| Refresh standards and formal evidence | Implemented baseline, abstraction map and release-selected ATP proof; full refinement and bounded ATP completion remain open. |
| Clarify battery, halt-charging and economic claims | Implemented in source generators, generated evidence and the public front door. |
| Test combined degraded charging operation | Existing deterministic cases retained; deployment timetable combinations remain an explicit gap. |
| Add more viaduct families | Rejected for v0.3: retain Pi25, Pi20 and the documented segmental fallback; resolve haul/lift choice and foundations from city logistics and geotechnical evidence. |
| Claim production-ready train/civil packages | Rejected until supplier freeze, structural/bench proof, first articles and deployment QA records exist. |
| Trace CAD through physical evidence and cost actuals | Accepted as the next vertical delivery method, not represented as completed evidence. |

## Compatibility

The project is pre-1.0. Generated packages should be regenerated from the v0.3
sources. Git revisions remain the review/history mechanism; deployment actuals
remain controlled separately in Ops Core.

Use the setup and verification commands from the root README. A tag is created
only after the [release checklist](releases.md) is fully satisfied on a clean
commit.
