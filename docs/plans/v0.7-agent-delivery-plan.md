# v0.7 agent delivery and tool migration plan

Status: ready for task decomposition and execution. Source baseline: main
`a16e9429cf55eec5a2c466eed7a2d1a32cf4601f`, reviewed 12 November 2026.

Deliver one continuous Workbench journey from a Samawah corridor revision through
service, civil quantities, fourteen-scope costs, a vehicle door-operator
manufacturing package, QA and maintenance. Repeat the corridor journey on one
Baghdad corridor. Increase Rust computation and use SolidCraft, FieldCraft and
RustGIS as preferred tools in demonstrated domains. Remove superseded production
paths and heavyweight default dependencies as their replacements pass the gates
below. Preserve independently useful solvers and historical evidence in optional
verification/replay installations.

This is an execution plan, not a declaration that tool migrations or engineering
qualification have happened. It extends the [roadmap](../ROADMAP.md); the
published v0.6.1 handover is complete and is not a recurring work package.

## Agent organisation and ownership

Use the existing `.codex/agents/` roles. The coordinator owns the task ledger,
interfaces, integration, main and publication. Specialists own bounded source
changes; numerical workers produce immutable run packages and never integrate.
The existing project configuration allows three concurrent threads per session:
plan for coordinator plus two specialists. Subagents consume those same slots;
a lead delegates serially or releases its slot. Do not spawn the entire hierarchy
at once or create a checkout per parameter sample.

| Lead role | Bounded subagent responsibilities | Source ownership |
|---|---|---|
| coordinator | Project identity, dependency ledger, release scope | Campaign/task definitions, shared schemas, integration and roadmap |
| service | Corridor/service/cost continuity; GIS revision loop; Baghdad replay | `engineering/outline/`, `engineering/rustgis/`, existing routing/alignment bridges |
| mechanical | Installed vehicle; door geometry; motion/access/removal; controlled drawings | `engineering/vehicle_parts/`, new door modules in existing CAD adapters, owned installation adapters |
| civil | Span/support/station; bearings and load cases; erection/lifting | `engineering/design_search/craft_backends/viaduct_*`, candidate-specific civil records |
| electrical | Available-force/braking maps; door wiring/power; thermal duty | Existing station-rail/electrical models and allocated door electrical definitions |
| twin | CAD/BOM/IFC consistency; manufacturing/QA; lifecycle integration | `engineering/pilot_delivery/`, delivery exports and `services/integration/` |
| verifier | Differential numerical checks, identity/tamper checks, independent solver and clean-install review | Verification fixtures/reports; no ownership of the implementation being reviewed |
| bounded software specialists | Rust kernels, profiling, Workbench, runtime/storage, packaging | Explicit files allocated by coordinator under the leads above; no blanket ownership of all `engineering/` |

File ownership is per assignment, not permanent team territory. For example,
service owns `city_workflow.py` integration while a Rust subagent owns its new
kernel and bridge; the coordinator applies shared call-site changes after the
kernel lands. Every assignment states: “You are not alone in the codebase;
preserve other edits and adapt to integrated changes.” Review is separate from
authorship; AI peer review does not supply physical measurements or a person's
identity/signature.

## Task contract and execution ledger

The coordinator creates a machine-readable task ledger before implementation.
Each task has the following contract; these are proposed fields, not a claim
that a new dispatcher already exists:

```yaml
task_id: R02
parent_task: R01
owner_role: service
status: planned
source_commit: EXACT_COMMIT
candidate_ids: {physical: EXACT_ID, component: EXACT_ID}
evaluation_context: {provider: PIN, material: HASH, load: HASH, mesh: HASH}
requires: [R01, P01]
owned_paths: [EXPLICIT_FILES]
fixed_interfaces: [SCHEMA_AND_UNITS]
allowed_variables: [ONE_PROFILED_KERNEL_IMPLEMENTATION]
requirements: [SUPPORTED_REQUIREMENT_IDS]
resource_class: software
resources:
  maximum_memory_mib: 2048
  maximum_scratch_mib: 1024
  maximum_output_mib: 128
  maximum_build_cache_mib: 512
  maximum_wall_seconds: 600
  maximum_processes: 1
  threads_per_process: 1
trial_limit: 1 cold plus 3 paired warm trials
completion: [PARITY, END_TO_END_BENEFIT, REVIEW]
artifacts: [INPUTS, OUTPUTS, LOGS, HASHES, BENCHMARK, REVIEW]
next_if_blocked: NAMED_MEASUREMENT_OR_INTERFACE_TASK
```

Replace the example resource values with measured/requested limits for each
assignment before it becomes ready. All resource fields are mandatory, including
CAD/FEA disk and build-cache growth. Reserve the combined scratch, output, build
and download growth across active jobs above the host reserve; reject an
incomplete request rather than inferring zero.

Use planned → ready → running → review → integrated. Deferred resource jobs
retain their queue position and inputs; failed/nonconverged/model-domain results
remain evidence with a next action. Software execution, numerical validity,
engineering screen, evidence maturity and physical acceptance are separate fields.
After two unsuccessful local revisions, review the model/domain or change family
instead of blindly extending a sweep. An agent stops at its trial/runtime budget,
returns the package and next experiment, and does not weaken an obligation.

Each handoff contains source commit/tree and dirty-state receipt; exact candidate,
request, material/load/mesh/tool/build identities; commands and environment;
input/output hashes; stdout/stderr and failure records; wall/CPU/RSS/I/O/scratch
measurements; units and numerical comparisons; dependency invalidations; tests;
remaining findings and a reproducible next command. Source edits are committed
before native runs. No source edits during a benchmark. Root integrates only the
owned change after review and preserves unrelated user edits.

## Rust migration policy and success measures

Extend `crates/osr-design-search`, `native_canonical.py`, `native_search.py`,
`crates/osr-routing`, `crates/osr-alignment` and applicable station-pair kernels.
Keep orchestration, policy assembly and readable evidence contracts in Python
where that is efficient. Avoid duplicating complete cost/service policy in two
languages. New Rust crates require a clear domain boundary, typed errors,
versioned input/output schemas, pinned build/ABI receipts and documented callers.

For each port, record total runtime including data conversion, extension loading,
serialization, build/install time, peak memory and disk. Use one cold and at least
three paired warm trials on identical hardware/inputs. Report distributions and
raw trials; increase repeats only if variance prevents a decision. A provisional
promotion target is at least 20% improvement in the measured affected stage and
no material end-to-end regression; the coordinator may accept a smaller speed
benefit for demonstrated memory/maintenance gains with an explicit rationale.
These are decision targets, not promised performance improvements. An unhelpful
port remains experimental or is removed from production.

Exact identities and canonical bytes must remain exact. Cover negative zero,
large integers, bool/int distinctions, Unicode, non-finite values, unknown/None,
cycles, JS integral-number transport and unsupported values. Preserve summation,
rounding, fleet ceiling and near-limit decisions. Where numerical output cannot
remain bit-identical, declare tolerances before testing and a new evaluation
implementation identity. Do not reuse historical hashes under changed arithmetic.
Vectorisation/SIMD/parallel reductions must pass the same criteria. Start with
bounded batches and deterministic reductions; avoid competing nested BLAS/Rayon
thread pools. Retain a small reference oracle after removing production fallback.

Change-bound current evidence is regenerated only for affected scopes or shown
held. Broad atlas/compiler changes need a measured reason and a costed refresh;
a local UI feature does not justify regenerating all 266 cities.

## CAD FEA and GIS promotion and legacy retirement

Current repository pins and demonstrations define the starting domain, not the
latest upstream feature list. SolidCraft 0.30.1/FieldCraft 0.7.5 is the tested
pair; the recorded SolidCraft 0.40.0-rc.2 format-50 import into FieldCraft's
format-48 reader failed. RustGIS is pinned at 0.5.0. T01 may test newer versions
in an isolated compatibility matrix, with new tool identities and retained
failures. No automatic “latest” upgrade.

SolidCraft's command engine exposes JSON commands across its CLI and agent
interfaces, which makes it a suitable preferred automation target
([upstream command documentation](https://docs.solidcraft.io/dev/commands.html)).
FieldCraft and RustGIS are Rust projects with broader advertised capabilities
([FieldCraft](https://github.com/tangency-labs/fieldcraft),
[RustGIS](https://github.com/opengeos/RustGIS)); upstream declarations are inputs
to admission tests, not evidence that the pinned OSR adapters support every case.

| Tool or path | v0.7 intended disposition | Required evidence before removal/switch |
|---|---|---|
| SolidCraft | Preferred CAD for demonstrated door/civil operations | Named part/placement identity, exact volume/centroid/bounds, holes/features, native/STEP reopen, editable history where required, manufacturing exports and motion/removal results |
| FieldCraft | Preferred mechanics for admitted material/load/joint domains | Analytical controls, mesh sensitivity/convergence, force/moment/energy residuals, representative assembly and independent comparison; unsupported cases explicitly routed/held |
| RustGIS | Preferred native corridor edit/reprice interface | Fresh two-edit Samawah cycle, Baghdad replay, CRS/topology/ID preservation, malicious/stale input rejection, bounded headless execution |
| FreeCAD | Remove from default migrated CAD installation; retain optional verification/replay initially | All current consumers of removed path migrated; independent exact B-rep checks remain available; drawings and editable exports meet requirements |
| CalculiX | Remove from default migrated mechanics installation; retain independent optional solver initially | Equivalent admitted scope and independent check route demonstrated; compare the same loads/materials/mesh meaning, not just similarly named cases |
| QGIS | Remove obsolete install/runtime requirements where any remain | It is already not required by current generation. Preserve lightweight historical `.qgz` ZIP/XML readers and source geography |
| Gmsh/OpenCASCADE meshing | Retain where currently needed | Current successful viaduct route uses conformal tet10 after native shared-prism hex meshing failed. Remove only after equivalent conformal mesh/connectivity/quality controls succeed |
| GetDP | Retain electromagnetic specialist scope | No equivalent validated electromagnetic replacement is established by the static mechanics pilot |
| IfcOpenShell/Bonsai | Keep IFC interoperability; make optional where supported | CAD replacement does not replace BIM relationships, georeferencing or IFC export validation |
| Chrono/SUMO | Inventory and isolate specialist usage | Multibody/network simulation needs independent replacement evidence; do not infer replacement from static FEA or a city cost model |
| Duplicate launchers, unconditional installers, stale UI branches | First deletion candidates | No active consumer, tested redirect or replacement, documented migration and historical replay path |

The existing 12-span CAD comparison and two coarse/fine mechanics cases are a
starting point. Homogeneous uncracked concrete, perfect bonding and bilateral
restraints do not establish bearing/contact, reinforcement/prestress, buckling,
fatigue or actual erection behaviour. Treat each required material/physics domain
as a separate admission task. Compare stresses at equivalent locations and
recovery definitions; a nodal sample is not a global integration-point maximum.
Two mesh levels can reveal error without establishing convergence.

Each retirement progresses through **inventory → compatible controls → actual
assembly/journey → preferred opt-in → default promotion → remove default install
→ remove unused active adapter**. For each path, retain a registry entry with
consumers, model domain, replacement, parity evidence, performance/installation
footprint, migration instruction, replay location, rollback and final status.
Default removal and source deletion are separate decisions. A heavy GUI can
leave normal installs while an isolated command-line verifier remains useful.

Before deleting active code, verify all callers, generators, imports, schemas,
CI installers and historical readers; test with the removed tool genuinely
absent. Missing backends produce a precise unsupported-operation message, never
a silent change of solver or physics. Keep original evidence bytes/hashes and
pinned replay instructions; archives need not remain normal checkout payloads.
No Git history rewrite is part of v0.7. Removing an adapter is not permission to
uninstall a user's unrelated system installation.

## Resources storage and isolation

Run `./osr perf storage` and admission checks at session start, before native jobs,
after each completed batch and before publication. Extend existing `measure`,
`compare` and cleanup facilities rather than introducing another profiler. Use
sparse worktrees for code/docs and shared read-only source artifacts; no full
checkout per agent or numerical sample. Keep private run directories outside
source. Limit Rust target caches per pinned toolchain; set bounded build threads.

Maintain 20 GiB host free reserve plus all outstanding job reservations. At the
last completed milestone there was about 22.4 GiB free, leaving only about 2.4 GiB
for new allocated scratch; remeasure live before admission. Count worktree,
build, download, archive and output growth, not just solver files. Parallel jobs
are limited by CPU, RAM and disk after reserves; start with one native job.

| Budget class | Initial assignment limit |
|---|---|
| inventory | Read-only discovery, no installs/solves; 15 minutes per bounded audit |
| software | One owned change/review slice; at most two failed local iterations before reassessment; relevant tests under a declared 10-minute allowance; 1 GiB scratch request |
| benchmark | One hotspot; one cold plus three paired warm trials; 10-minute total run budget, 2 GiB scratch, one numerical worker |
| CAD | One assembly, one bounded revision; initial 25-part pilot ceiling or explicit counted expansion; one process at a time, 120 seconds/2 GiB address space per pilot process; predeclare total process count |
| mechanics | One admitted case at two mesh levels and one independent comparison; initial application slice at most 8 native processes/30 minutes total; per-process budgets from its existing recipe, revised only with a new resource identity |
| GIS | One selected city at a time; retain current 60 CPU/75 wall seconds and 2 GiB address-space bounds per native process, 32 MiB upload, 2 MiB request and 256 MiB successful ZIP cache |
| integration | One fresh disposable environment and one named journey at a time; inventory image/dependency sizes first and defer until the measured reserve fits; 15-minute browser-job ceiling initially |

The full existing backend pilot has its own ≤32-process contract; do not squeeze
it into the 8-process application slice or silently enlarge either. A fine box
already required a separately recorded 3 GiB resource revision after a 2 GiB
failure. New larger models need explicit measured budgets, not repeated retries.
Thread budgets do not establish process-tree containment. Record bubblewrap,
Flatpak, cgroup/quota and monitoring actually applied. GNU time, sampled directory
size and RLIMIT_FSIZE do not enforce aggregate disk quotas.

Cleanup automatically only owned reproducible scratch/cache whose jobs are
terminal. Inventory dirty worktrees and ownership before proposing cleanup.
Preserve failed/nonconverged/interrupted evidence. For large research payloads,
copy to the chosen artifact backend, verify original and stored bytes, create
source-bound retrieval manifests, test offline/online replay, then retire
redundant working copies. Choose the backend and retention/backup responsibility
in S01; do not pretend an archive service already exists. Quarantine uncertain
material and request a concrete deletion decision rather than guessing ownership.

## Delivery waves and completion

These are sequencing estimates for the current small team, not a promise that
supplier tests can be completed on a software timetable.

| Wave | Typical window | Coordinator exit decision |
|---|---|---|
| 0 | First 1–2 days | P00/P01, T01 and R01 inventories/baselines; runnable ledger with ownership; next two bounded assignments ready |
| 1 | Weeks 1–2 | P02, first useful R02/R03 slice and S01; current-source Samawah GIS path demonstrable; early Workbench project continuity |
| 2 | Weeks 3–5 | C01/F01/C02/E01 with independently reviewed domain controls; expanded CAD/FEA use; measured Rust increments |
| 3 | Weeks 5–7 | M01/L01/W01 candidate-linked module lifecycle and dossier; G02 Baghdad generalisation |
| 4 | Weeks 8–10 | D01 supported-scope retirement, clean-install V01, regression evidence, supported release scope and open physical milestones |

Release acceptance requires both city journeys and a candidate-linked door
manufacturing/QA/maintenance journey, with source-consistent geometry, BOM,
costs and dossier. Tests cover invalid/stale/tampered input, resource refusal,
interruption/resume, rollback, supported exports, unavailable tools and clean
installation. Performance evidence includes cold/warm stage times, native rerun
counts, peak memory/disk and installation footprint. An unchanged repeat should
run no unnecessary native solver; a station edit should reuse unchanged vehicle
and manufacturing results. Report remaining physical limits at their affected
results, not as hidden assumptions or zero-valued inputs.

CI keeps fast contracts on relevant changes, integration on interface changes,
and heavy numerical runs on explicit campaigns. Each Rust/provider change gets
focused parity tests; repeat complete journeys only for changed dependencies or
unresolved concerns. Preserve the existing sparse-test coverage guard. Tests and
artifact records bind their actual source commits; never relabel old execution.

The coordinator closes tasks when outputs, review and dependency propagation are
complete. If supplier data, a material model or an actual test is missing, record
the specific evidence request and advance independent work. Software may publish
a reproducible bounded planning capability with visible open physical findings;
manufacturing release and physical qualification require their actual evidence.
Use the existing maintainer software-release process, without adding a new
signature bureaucracy or reopening v0.6.1.

## Immediate agent dispatch

1. Coordinator creates P00/P01 ledger entries and assigns explicit files/resource
   requests. Do not change agent permissions or increase configured concurrency.
2. Slot A: performance specialist runs R01 on the retained Samawah baseline and
   prepares a ranked first Rust port. Slot B: tool-interface specialist produces
   T01, including every active legacy consumer and installation footprint.
3. After those reviews, slot A implements the smallest justified R02 slice,
   or R03 once P01 is integrated;
   slot B diagnoses G01's exact current-source binding and import-custody gaps.
   Coordinator lands P01/P02 interfaces before G01 execution/integration, without
   concurrent writers to shared files.
4. Schedule independent verifier slices before promotion, then rotate the same
   slots through door/civil/electrical work and the lifecycle chain. Keep blocked
   external evidence visible in the ledger while scheduling ready tasks.
